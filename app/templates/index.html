      Certificate Import Guide

      How to create, export, and install certificates for each template.

      Quick Start

      1. Create a Root CA — click + New CA, enter your domain, and choose an algorithm. For maximum Windows compatibility use RSA 4096 or ECDSA P-384.
      2. Issue a certificate — select the CA, click + Issue Certificate, pick a template, and fill in the common name.
      3. Export as PKCS12 (.pfx) — this is the default format. A PFX password is required for Windows import; it defaults to changeit.
      4. Trust the CA on your machine — export the CA certificate (Certificate Only, DER format) and import it into Trusted Root Certification Authorities. Without this step, certificates will appear untrusted.
      All certificates are self-signed by your CA. They are only trusted on machines where you have installed the CA certificate as a trusted root.

      Windows Certificate Store Tip

      When importing into a Windows certificate store, the import wizard only shows top-level store names like Personal — you will not see a Personal → Certificates subfolder during import. This is normal. Just select Personal and finish the import. The certificate will appear under Personal → Certificates once the import is complete — the Certificates subfolder is created automatically by the MMC snap-in to organize the store contents.

      Export Formats

      • PKCS12 (.pfx) — bundles cert + private key + CA chain into one file. Required for importing into Windows certificate stores. Always password-protected.
      • PEM — base64-encoded text format. Used by Apache, Nginx, Linux tools, and OpenSSL. Not directly importable into Windows cert stores.
      • DER — binary certificate format (no private key). Use for importing public certificates.
      • CRT (.crt) — same as DER but with the .crt extension that Windows recognizes natively. Double-click to open the certificate viewer or import wizard.

      Installing the Root CA on Windows

      1. Select your Root CA in the sidebar.
      2. Export with format DER, include Certificate Only.
      3. Open the exported .der file from your Downloads folder.
      4. Click Install Certificate → Local Machine → Place all certificates in the following store → Browse → Trusted Root Certification Authorities → Finish.
      You must install the CA as a trusted root before importing any certificates it issued. Otherwise Windows will mark them as untrusted.

      Installing the Root CA on macOS

      1. Export the CA as DER, Certificate Only.
      2. Double-click the file to add it to Keychain Access.
      3. In Keychain Access, find the CA, double-click it, expand Trust, and set to Always Trust.

      Installing the Root CA on Linux

      1. Export the CA as PEM, Certificate Only.
      2. Copy to /usr/local/share/ca-certificates/your-ca.crt
      3. Run sudo update-ca-certificates

      Computer Certificate

      Used for machine identity — allows a Windows computer to authenticate to the network and to services. Includes both Client Authentication and Server Authentication extended key usage.

      When to Use

      • 802.1X network authentication (wired or wireless)
      • IPsec / VPN machine certificates
      • SCCM / Intune device identity
      • Machine-to-machine TLS (mutual auth)

      Creating the Certificate

      1. Select your CA, click + Issue Certificate.
      2. Template: Computer.
      3. Common Name: the machine's FQDN, e.g. WORKSTATION01.corp.example.com.
      4. SANs: add the FQDN and optionally the short hostname.
      5. Algorithm: RSA 4096 or ECDSA P-384 for best Windows compatibility.

      Importing into Windows (Personal Store)

      1. Export as PKCS12 (.pfx), include Certificate + Key, with a password (default: changeit).
      2. Open certlm.msc (Local Computer certificates) — press Win+R, type certlm.msc, press Enter.
      3. Right-click Personal → All Tasks → Import.
      4. Browse to the .pfx file, enter the password.
      5. Choose Place all certificates in the following store → Personal.
      6. Finish. The certificate will appear under Personal → Certificates (the subfolder is created automatically).
      Use certlm.msc (Local Machine) for computer certificates, not certmgr.msc (Current User). Computer certificates must be in the Local Machine store to be used for machine authentication.
      You must also install the issuing CA into Trusted Root Certification Authorities (see General tab) or the certificate will show as untrusted.

      Web Server Certificate

      Standard TLS/SSL certificate for HTTPS services. Includes Server Authentication extended key usage.

      When to Use

      • Internal web servers, APIs, dashboards
      • Development / staging HTTPS
      • Reverse proxies (Nginx, Apache, IIS)

      Creating the Certificate

      1. Template: Web Server.
      2. Common Name: the server's FQDN, e.g. app.example.com.
      3. SANs: add all hostnames and domains the server will respond to. Browsers require a SAN match.

      Installing on IIS (Windows)

      1. Export as PKCS12 (.pfx) with Certificate + Key.
      2. Open IIS Manager → server node → Server Certificates → Import.
      3. Browse to the .pfx file, enter the password, select store Personal.
      4. Edit your site bindings → add HTTPS binding → select the imported certificate.

      Installing on Nginx / Apache (Linux)

      1. Export as PEM, Certificate + Key.
      2. Split the file: the first PEM block is the certificate, the second is the private key.
      3. Or export separately: Certificate Only (PEM) and Private Key Only (PEM).
      4. Nginx: ssl_certificate /path/to/cert.pem; ssl_certificate_key /path/to/key.pem;
      5. Apache: SSLCertificateFile and SSLCertificateKeyFile directives.
      For the full trust chain, export the certificate with Full Chain (cert + CA) and use that as the certificate file.

      Client Authentication Certificate

      Used for user identity — authenticates a person or service account to a server. Includes Client Authentication extended key usage only.

      When to Use

      • Mutual TLS (mTLS) client identity
      • VPN user certificates
      • Smart card logon (with additional configuration)
      • API client authentication

      Creating the Certificate

      1. Template: Client Authentication.
      2. Common Name: the user or service identity, e.g. john.doe@example.com or svc-api-client.

      Importing into Windows (Current User)

      1. Export as PKCS12 (.pfx) with Certificate + Key.
      2. Double-click the .pfx file, or open certmgr.msc (Current User).
      3. Import into the Personal store (you will only see Personal, not a Certificates subfolder — this is normal).
      4. Enter the PFX password when prompted.
      For user certificates, use certmgr.msc (Current User). For service accounts running as SYSTEM, use certlm.msc (Local Machine).

      User Certificate

      Used for user identity on Windows — authenticates a person for smart card logon, VPN, Wi-Fi (802.1X), and mTLS. Includes Client Authentication and Smart Card Logon extended key usage, with a Microsoft UPN in the Subject Alternative Name.

      When to Use

      • Smart card or virtual smart card logon
      • 802.1X wireless/wired user authentication
      • VPN user certificates
      • mTLS client identity with Windows SSO
      • Conditional Access certificate-based authentication

      Creating the Certificate

      1. Template: User.
      2. Common Name: the user's display name, e.g. John Doe.
      3. Email Address: the user's email, e.g. john.doe@example.com.
      4. User Principal Name (UPN): the Windows logon UPN, e.g. john.doe@corp.example.com. This is embedded as a Microsoft UPN OtherName in the SAN — required for Windows smart card logon.
      5. Optionally check Include CRL Distribution Point to add offline revocation checking (see the CRL tab).

      Importing into Windows (Current User)

      1. Export as PKCS12 (.pfx) with Certificate + Key.
      2. Double-click the .pfx file, or open certmgr.msc (Current User).
      3. Import into the Personal store.
      4. Enter the PFX password when prompted.
      The UPN in the certificate must match the user's UPN in Active Directory or Entra ID for smart card logon to work.
      You must also install the issuing CA into Trusted Root Certification Authorities and (if using CRL) import the CA's CRL file. See the General and CRL tabs.

      Code Signing Certificate

      Used to digitally sign executables, scripts, and drivers. Includes Code Signing extended key usage.

      When to Use

      • Signing internal PowerShell scripts
      • Signing internal executables or DLLs
      • Testing Authenticode signature workflows
      • Driver signing (test mode)

      Creating the Certificate

      1. Template: Code Signing.
      2. Common Name: your organization or team name, e.g. Corp IT Code Signing.

      Importing and Using on Windows

      1. Export as PKCS12 (.pfx) with Certificate + Key.
      2. Open certmgr.msc, right-click Personal → All Tasks → Import. Select the Personal store when prompted.
      3. Sign a PowerShell script: Set-AuthenticodeSignature -FilePath script.ps1 -Certificate (Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert)
      4. Sign an EXE with signtool: signtool sign /fd SHA256 /f cert.pfx /p changeit app.exe
      Self-signed code signing certificates will trigger SmartScreen and trust warnings. To suppress these on managed machines, install the CA into Trusted Root Certification Authorities and the code signing cert into Trusted Publishers.

      Email (S/MIME) Certificate

      Used to sign and encrypt email messages. Includes Email Protection extended key usage, and embeds the email address in the Subject and SANs.

      When to Use

      • Signing outgoing email (proves sender identity)
      • Encrypting email contents (recipient needs your public cert)
      • Testing S/MIME workflows in Outlook, Thunderbird, etc.

      Creating the Certificate

      1. Template: Email (S/MIME).
      2. Common Name: the user's name, e.g. John Doe.
      3. Email Address: the exact email to sign/encrypt for, e.g. john.doe@example.com.

      Setting Up in Outlook (Windows)

      1. Export as PKCS12 (.pfx) with Certificate + Key.
      2. Double-click the .pfx file to import into Personal store (Current User).
      3. In Outlook: File → Options → Trust Center → Trust Center Settings → Email Security.
      4. Under Encrypted email, click Settings → Choose next to Signing/Encryption Certificate → select your certificate.

      Setting Up in Thunderbird

      1. Export as PKCS12 (.pfx) with Certificate + Key.
      2. In Thunderbird: Account Settings → End-To-End Encryption → S/MIME.
      3. Click Manage S/MIME Certificates → Your Certificates → Import → select the .pfx file.
      4. Select the certificate for both signing and encryption.
      Both sender and recipient need each other's public certificate to exchange encrypted email. Share the public certificate (DER export, Certificate Only) with your correspondents.

      Offline CRL (Certificate Revocation List)

      This tool generates locally-signed CRL files to provide offline revocation status for issued certificates. This is not a live revocation service — it is a generated artifact that must be manually imported into the Windows certificate store on each endpoint.

      How It Works

      1. When issuing a certificate, check Include CRL Distribution Point. This embeds a CDP extension in the certificate with a placeholder URL (http://pki.<domain>/crl/...).
      2. On the CA details page, click Export CRL to generate and download a .crl file. This file is cryptographically signed by the CA and lists any certificates you have revoked.
      3. Import the .crl file into the Windows certificate store on the target endpoint. Windows caches the CRL locally and uses it for revocation checks — no network fetch needed.

      Importing the CRL on Windows

      1. Open certlm.msc (Local Machine) or certmgr.msc (Current User).
      2. Navigate to Intermediate Certification Authorities.
      3. Right-click → All Tasks → Import.
      4. Browse to the .crl file, select it, and finish the import.
      5. The CRL will appear under Certificate Revocation Lists within that store.
      The CRL is valid for 10 years by default. If you revoke a certificate after importing the CRL, you must re-export and re-import the updated CRL on each endpoint for the revocation to take effect.

      Important: This Is a Generated CRL, Not a Live Service

      The CDP URL in the certificate (http://pki.<domain>/crl/...) is a placeholder — there is no server listening at that address. The revocation check works because Windows finds the CRL already cached in the local certificate store, so it never needs to fetch from the URL.

      This approach is suitable for:

      • Posture and security demos where certificates need to pass Windows validation
      • Lab and test environments
      • Scenarios where you control the endpoints and can import the CRL manually
      This is not equivalent to a production PKI with a live CRL server or OCSP responder. The CRL is a static file that must be manually updated and redistributed when certificates are revoked.

      PowerShell Import (Alternative)

      You can also import the CRL via PowerShell:

      certutil -addstore CA "path\to\ca-name.crl"

      Run as Administrator for the Local Machine store.

      Exports all CAs, certificates, and SSH keys into a single AES-256 encrypted file saved to your Downloads folder.

      SSH Key Guide

      How to generate, export, and use SSH key pairs.

      What This Tool Does

      Generates SSH key pairs and stores them in an encrypted database. Keys are saved directly to disk on export, avoiding clipboard line-ending corruption that commonly breaks private keys on Windows.

      Supported Algorithms

      • RSA 4096 (default) — broadest compatibility with legacy systems, firewalls, network gear, and older SSH servers. Works with Bitwarden SSH agent.
      • Ed25519 — modern, fast, small keys. Works with Bitwarden SSH agent. Preferred for new deployments.
      • ECDSA P-256 / P-384 — good performance and security. Not compatible with Bitwarden's SSH agent.
      • RSA 2048 — legacy fallback only. Use RSA 4096 instead.

      Export Formats

      • OpenSSH (default) — -----BEGIN OPENSSH PRIVATE KEY----- format. Used by OpenSSH, Git, and most modern tools. Compatible with Bitwarden.
      • PEM (PKCS#8) — -----BEGIN PRIVATE KEY----- format. Used by older tools, Java, and some enterprise software. Also compatible with Bitwarden.

      Passphrase Protection

      Optionally encrypt the private key with a passphrase at generation time. You will be prompted for it each time the key is used. You can also add a passphrase during export without having set one at generation.

      Keys without a passphrase grant access to anyone who obtains the file. Use a passphrase for production keys.

      Importing into Bitwarden

      Bitwarden can store SSH keys and use them via its SSH agent, so you never need the private key file on disk.

      1. Select your SSH key in the sidebar.
      2. Click Copy Private Key (Bitwarden) — this copies the full PEM-formatted private key to your clipboard.
      3. In Bitwarden, create a new SSH Key item.
      4. Paste the private key into the Private Key field. Bitwarden will auto-detect the format and extract the public key and fingerprint.
      Bitwarden's SSH agent supports RSA and Ed25519 keys only. ECDSA keys cannot be used with the Bitwarden SSH agent.

      Using the Bitwarden SSH Agent

      1. Enable the SSH agent in Bitwarden Settings → SSH Agent.
      2. Configure your SSH client to use Bitwarden's agent socket (Bitwarden sets the SSH_AUTH_SOCK environment variable automatically on most platforms).
      3. When you ssh to a server, Bitwarden prompts you to approve the key usage.
      The private key must include the full PEM header and footer (-----BEGIN ... ----- / -----END ... -----). The Copy Private Key button includes these automatically.

      Using on Linux / macOS

      1. Export the private key: select Private Key, format OpenSSH, click Download.
      2. Move the downloaded file to your SSH directory:
        mv ~/Downloads/keyname-id_key ~/.ssh/id_rsa
      3. Set correct permissions:
        chmod 600 ~/.ssh/id_rsa
      4. Export the public key separately, or click Copy Public Key and paste into ~/.ssh/id_rsa.pub.

      Adding to the SSH Agent

      ssh-add ~/.ssh/id_rsa

      If the key has a passphrase, you will be prompted to enter it once.

      Deploying the Public Key

      Copy the public key to the target server:

      ssh-copy-id -i ~/.ssh/id_rsa.pub user@hostname

      Or manually append to ~/.ssh/authorized_keys on the server.

      The private key file must have 600 permissions. SSH refuses to use a key with permissions that are too open.

      Using on Windows (OpenSSH)

      Windows 10/11 includes OpenSSH as a built-in optional feature.

      1. Export the private key in OpenSSH format.
      2. Move the file to C:\Users\<you>\.ssh\ (create the folder if it does not exist).
      3. Rename it to match the expected name, e.g. id_rsa or id_ed25519.

      Windows SSH Agent

      1. Open Services (services.msc) and set OpenSSH Authentication Agent to Automatic, then start it.
      2. Run: ssh-add C:\Users\<you>\.ssh\id_rsa

      Using with PuTTY

      PuTTY requires its own PPK format. To convert:

      1. Export the key in OpenSSH format.
      2. Open PuTTYgen → Conversions → Import key → select the file.
      3. Click Save private key to create a .ppk file.
      Direct download avoids the line-ending corruption that happens when pasting private keys through Windows clipboard into text editors. Always use the Download button rather than copy-pasting key files.

      Adding to GitHub

      1. Click Copy Public Key in the key detail view.
      2. Go to GitHub → Settings → SSH and GPG keys → New SSH key.
      3. Paste the public key and give it a descriptive title.

      Adding to GitLab

      1. Click Copy Public Key.
      2. Go to GitLab → Preferences → SSH Keys.
      3. Paste and optionally set an expiration date.

      Deploy Keys (Read-Only)

      For CI/CD or read-only repo access, add the public key as a Deploy Key on the repository settings page instead of your user account.

      Use Ed25519 for GitHub and GitLab — it is their recommended algorithm and produces the smallest keys.

      Encryption Settings

      Database encryption is OFF. Private keys (CA keys, certificate keys, SSH private keys) are stored in plaintext in the SQLite database.

      What this protects: If someone copies your database file (~/.cert-generator/certs.db), they cannot read your private keys without the master password.

      What this does NOT protect: While the app is running and unlocked, keys are decrypted in memory. This protects data at rest, not a running application.

      Warning: If you forget your password, your private keys are unrecoverable. Use the Backup feature to create an encrypted backup before enabling.

      Database encryption is ON. Private keys are encrypted with AES-256-GCM using your master password.
